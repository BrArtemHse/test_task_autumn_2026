# План реализации Авито.Кухни

Этот документ фиксирует план, по которому MVP проектировался и реализовывался с помощью ИИ-ассистента. Архитектурные решения проверялись вручную и закреплялись тестами.

## Цель

Реализовать в одном репозитории backend MVP, который позволяет пользователю выбрать доступные позиции, создать заказ и получить решение заведения. В состав проекта должен входить отдельный демонстрационный сервис ресторана.

## Архитектурный подход

- HTTP/JSON и OpenAPI используются для web-клиента и внешней интеграции заведения.
- gRPC/protobuf используется для синхронных вызовов между внутренними сервисами.
- Apache Kafka передаёт события создания заказа и решения заведения асинхронно.
- PostgreSQL хранит каталог, заказы, интеграции, inbox и transactional outbox.
- Доставка событий считается at-least-once, поэтому все эффекты имеют устойчивые идентификаторы и выполняются идемпотентно.

## Последовательность реализации

1. Описать CJM пользователя и заведения, границы MVP и статусы заказа.
2. Разделить систему на `kitchen-api`, `catalog-service`, `order-service`, `partner-service` и `sample-restaurant-service`.
3. Зафиксировать внешние OpenAPI-контракты и внутренние protobuf-контракты.
4. Реализовать доменные инварианты и идемпотентное создание заказа.
5. Добавить PostgreSQL-схемы, миграции и тестовые данные каталога.
6. Реализовать публикацию через transactional outbox и обработку через inbox.
7. Добавить доставку заказа в API заведения, callback и операторскую авторизацию.
8. Добавить graceful shutdown, health endpoints, bounded retry зависимостей и статический анализ.
9. Подготовить единый Docker-образ сервисов, Kafka в KRaft-режиме, Compose и сквозной smoke-тест.
10. Проверить unit/integration-тесты, race detector, линтер, сборку и Linux Compose-сценарий.

## Критерии проверки

- Недоступную позицию нельзя заказать.
- Повтор с тем же `Idempotency-Key` не создаёт второй заказ.
- Заказ доходит до отдельного сервиса ресторана.
- Решение `accepted` или `rejected` возвращается в пользовательский API.
- Повторная доставка Kafka-события или callback не дублирует бизнес-эффект.
- Временная недоступность PostgreSQL или ресторана не приводит к мгновенной потере операции.

Основной автоматизированный приёмочный сценарий находится в `scripts/smoke.sh`.
