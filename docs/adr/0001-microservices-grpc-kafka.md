# ADR-0001: микросервисы, HTTP edge, gRPC и Kafka

## Статус

Принято.

## Контекст

Авито.Кухня должна показать архитектуру backend-системы, которую можно развивать после MVP. Задание требует API для web-клиента и заведений, OpenAPI, миграции, Docker Compose и отдельный сервис примерного заведения.

Web-клиенту нужен обычный HTTP API. Внутренним сервисам полезны строгие типизированные контракты. Интеграция с рестораном не должна удерживать пользовательский запрос и обязана переживать временную недоступность внешней системы.

## Решение

- Использовать HTTP/JSON и OpenAPI на границе web-клиента.
- Использовать HTTP callback и Bearer-токен на границе заведения.
- Использовать gRPC/protobuf между `kitchen-api`, `catalog-service` и `order-service`.
- Использовать Apache Kafka для асинхронного обмена событиями заказа.
- Использовать PostgreSQL с отдельными схемами-владельцами `catalog`, `orders` и `partner`.
- Использовать transactional outbox у производителей и inbox у потребителей.
- Считать доставку at-least-once и делать эффекты идемпотентными.
- Ограничить исполнимый ресторанный CJM решением `accepted/rejected`.

## Последствия

Положительные:

- Web API легко проверяется через OpenAPI и curl.
- Внутренние контракты типизированы и изолированы от HTTP DTO.
- Создание заказа не зависит от доступности ресторана в момент пользовательского запроса.
- Повторная публикация, доставка и callback не создают новый логический заказ или решение.
- Сервисы можно масштабировать независимо по их нагрузке.

Отрицательные:

- Для MVP требуется больше процессов и инфраструктуры, чем для модульного монолита.
- Межсервисная согласованность eventual, поэтому нужны явные статусы и идемпотентность.
- Локальному окружению нужны PostgreSQL и Apache Kafka в одновузловом KRaft-режиме.
- Poison event до появления quarantine/redrive блокирует свою Kafka-партицию.

## Почему MVP заканчивается решением заведения

Для выполнения задания достаточно замкнуть пользовательский и ресторанный сценарий: найти доступное блюдо, создать заказ, доставить его отдельному сервису заведения и вернуть решение. Переходы `preparing`, `ready` и `completed` сохранены в доменной state machine как направление развития, но не выдаются за реализованный внешний сценарий.

## Не входит в решение

- Аутентификация конечного пользователя.
- Платежи и возвраты.
- Назначение курьера.
- Геопоиск и ETA.
- Multi-region, service mesh и workflow engine.
